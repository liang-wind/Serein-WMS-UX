# 海外仓 WMS 差距分析

> 分析对象：`wms/` 目录下现有原型（7 个静态页面 + 5 个 assets 文件）
> 对标产品：易仓 ECCANG WMS、Flux WMS、万邑通 WinIt
> 日期：2026-10-11

---

## 1. 现状盘点

### 1.1 技术形态

| 项 | 现状 |
|---|---|
| 形态 | 纯静态原型（HTML + CSS + 原生 JS） |
| 后端 / 数据库 / 接口 | **无** |
| 数据层 | `assets/data.js` 中的 `WMS.DB` 内存对象（9 张表） |
| 交互层 | `assets/app.js`（表格渲染 / 筛选 / 排序 / 抽屉）、`assets/ui.js`（toast / confirm） |
| 状态持久化 | **无**，刷新页面即丢失 |
| 鉴权 / 审计 / 并发控制 | **无** |

### 1.2 已覆盖模块

| 页面 | 模块 | 实际深度 |
|---|---|---|
| `index.html` | 仓储总览：KPI、库容水位、异常预警、最近单据 | 展示级 |
| `inbound.html` | ASN 预约 → 收货 → 验收 → 上架、月台预约、流程 stepper | 流程完整，动作均为 toast |
| `inventory.html` | SKU 台账、可用/锁定/安全线、批次效期、水位分布 | 表格完整 |
| `outbound.html` | 波次、拣货/打包/交接、SLA、承运商进度 | 状态机展示，无策略 |
| `locations.html` | 库区热力图、库位类型、占用状态 | 展示级 |
| `reports.html` | 5 类报表 + 12 张报表库 + 吞吐柱状图 | 壳子 |
| `settings.html` | 基础信息、7 个策略开关、集成状态、3 角色用户表 | 壳子 |

### 1.3 定位判断（关键结论）

现有数据模型中的外部方只有 `supplier`（供应商），仓库主体是「环宇跨境供应链有限公司」——
即**这套系统是"自营仓 / 自有仓"视角**。

而 **易仓 / Flux / 万邑通 全部是 3PL 代管仓视角**：一栋楼里堆着多个卖家的货，
库存分开算、库位可共享、操作费各自定价、账各自结。

这一个定位差异，决定了后文约 80% 的缺口。

### 1.4 设计上值得保留的优点

- Design token 体系统一（`assets/wms.css`），色彩/间距/圆角规范一致；
- Bullet Chart（实测值 vs 目标线 + 三色区间）表达专业度高，是同类产品少见的细节；
- 抽屉详情 + timeline 的交互模式清晰；
- 无障碍处理扎实：`skip-link`、`aria-label`、`role="img"`、表格 `caption`、`scope="col"`；
- 筛选 / 排序 / tabs / 分页 / 状态徽章字典组件化程度高。

**结论：UI 层作为原型合格；数据层与业务层需要重做。**

## 3. P0 核心缺口（海外仓的"发动机"）

### 3.1 多货主 / 货权分离 —— 最大架构缺口

**证据**：`assets/data.js` 中 `sku` 表字段为
`id / name / cat / wh / loc / avail / lock / safety / status / cost / supplier / lastIn / turnover / velocity / bins / batches / note`，
**没有任何货主字段**。

**为什么是核心**：海外仓的基础业务是一栋楼堆多个卖家的货，必须货权分离、独立台账、独立计价。
做不到这点，系统只能服务一家公司，无法作为产品售卖。

**必须补**：
- `tenant` 货主实体，全表带 `tenant_id` 隔离；
- 商品 / 批次 / 库位 / 单据 / 账套全部归属货主；
- 货主协议（计费模板、效期规则、SLA、库位共享策略）；
- 「混放不混账」校验（同库位容纳多货主需显式配置）。

### 3.2 OMS 订单中心与自动分仓

**现状**：出库单在系统里是"天降"的，没有订单接入层。

**为什么是核心**：订单来自 Amazon / Shopify / eBay / Temu / TikTok / Walmart / ERP / 货主 API，
进系统后要做：地址解析清洗 → 库存预占 → 智能分仓（就近 / 库存深度 / 渠道匹配 / SLA）→ 拆合单 → 下发 WMS。
同时库存要回传平台，**这才是超卖拦截的真正落点**（`settings.html` 的"超卖拦截"开关目前没有数据支撑）。

**必须补**：平台授权与拉单、订单 ↔ 出货单映射、拆合单规则、库存同步回传、订单异常拦截（无货 / 地址不可达 / 超区）与工单。

### 3.3 计费与账务

**现状**：`reports.html` 中「仓储服务费账单」状态为"生成失败"，因为底层没有计费引擎。

**为什么是核心**：3PL 的收入完全依赖这一块——
仓储费（按 CBM/托盘/天，阶梯价）、入库操作费（按箱/件/SKU 种数）、出库操作费（按件/重量/票）、
包材费、增值服务费（换标/质检/拍照/销毁）、异常处理费、运费差价。

**必须补**：计费规则引擎（货主 × 计费项 × 阶梯/单价/最低消费）、**作业前费用预估与确认**（防白干）、
账单生成 / 对账 / 差异调整、收付款、账期与押金、发票、货主自助查账。

### 3.4 退件管理 / 逆向物流

**现状**：完全空白。入库只有"从供应商来"，出库只有"一件代发"。

**为什么是核心**：易仓将"退货换标"列为六大业务场景之一；Flux 同样覆盖；
万邑通有明确的 RMA 规则文档（"派送失败退回归仓后自动创建退货单并按卖家预设策略处理"）。
这块业务**最容易漏账、纠纷最多、毛利也最高**。

**必须补**：退货单创建（RMA / FBA 移除单 / 派送失败退回）→ 退件收货 → **质检分级**
（可售 / 待翻新 / 残损 / 报废）→ 换标 / 重新包装 / 翻新 → 重新上架或销毁 → 拍照留档 → 计费。

### 3.5 FBA 中转 / 备货转运

**对标**：易仓的"FBA 中转、分箱、箱唛、批次清晰可追溯"；万邑通的"FBA 送仓/转仓、Flexload 柔性备货"。

**必须补**：FBA Shipment Plan 创建、按箱规分箱、亚马逊箱唛打印、转运出仓单、
卡派 / LTL 预约与 POD 回传、头程在途库存跟踪。

### 3.6 PDA / RF 作业体系

**现状**：UI 仍是桌面端大表格；海外仓作业 100% 发生在手持终端。

**必须补**：
- PDA 专用界面（大按钮、断网续传、连续扫码）；
- RF 收货、RF 上架（库位扫码校验）、RF 拣货（路径引导 / 灯光 / 语音）、RF 盘点、RF 移库；
- 电子秤 / 标签打印机 / 扫描枪集成；
- 作业任务下发、回收与绩效采集。

### 3.7 波次策略与拣货打包闭环

**现状**：`outbound.html` 只有一个"生成波次"按钮 + 3 个进度条。

**必须补**：合波规则（仓库+渠道+承运商+截单时间）、拣货策略（分区拣 / 批量拣 / 播种墙 / 边拣边分）、
路径优化、二次分拣、**复核**、**称重校验**（防错发的关键节点，当前完全缺失）、包材推荐与耗材扣减。

## 4. P1 重要缺口

| 缺口 | 说明 |
|---|---|
| 库内作业闭环 | 移库、补货（存储位→拣货位）、理货、加工/组装/换包装、拆柜、库位整理。当前 `loc` 有"锁定/冻结"但无库内单据流 |
| 打印 / 标签中心 | 箱唛、面单、拣货单、条码标签、发票；需 ZPL/TSPL 渲染与打印机队列管理 |
| 物流管理 | 承运商账号池、面单申请、运费试算、轨迹抓取、妥投确认、异常上报、索赔。当前"轨迹停滞"只是告警，无闭环 |
| 盘点体系 | 明盘/盲盘、快照盘点、循环盘点（`settings.html` 有 02:00 开关但无任务流）、盘盈盘亏处理与审批、复盘 |
| 开放 API + Webhook + 沙箱 | 竞品均有开发者文档。没有 API 就接不进 ERP 与货主系统 |
| 货主自助门户 | 货主自主下单、查库存、查账单、下载报表、管理 API Key |
| 组织权限深化 | 当前仅 3 个角色的用户表。需 RBAC（菜单/按钮/数据范围到货主与仓库）+ 审批流 + 审计日志 |
| 多语言 / 多币种 / 多单位 | 币种硬编码 `$`；无 UOM 体系（箱↔件↔托盘↔重量/材积）。欧美仓必须 USD/EUR/GBP + lbs/kg + in/cm 换算 |
| B2B 大货 | 整托整柜出入库、LTL/FTL、卡派预约、POD、按托盘计费 |
| 头程 / 清关 | PO、装箱单、AMS/ISF、HTS 编码、关税。易仓以独立 TMS 产品线覆盖，万邑通以"万邑云链"覆盖 |

## 6. 数据模型硬伤（不改这些，功能堆不上去）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 无货主维度 | 多租户无从谈起，必须先给每张表加 `tenant_id` |
| 2 | 无库存流水（Ledger） | 只有一个 `avail / lock` 数字，无"在途/待检/待上架/冻结/可用"状态机，无法对账、无法追溯、无法做财务口径库存 |
| 3 | 无单据状态机 | ASN 五步仅是 `stepper` 视觉组件，不是可编排工作流（缺分支：免检跳过、部分收货、异常挂起） |
| 4 | 无计量体系 | "箱 / 件 / kg" 混用且不可换算，计费与运费试算无从算起 |
| 5 | 库位模型过薄 | 仅为 `A-03-12` 字符串 + 类型，无容量/承重/体积/混料规则/动线，无法做上架推荐与库容规划 |
| 6 | 无服务层 | 所有"操作"是 `data-toast`，无 API、鉴权、幂等、并发控制。上真实场景第一天就会超卖和丢单 |

## 7. 结论

这套系统在"仓内作业可视化"上达到了漂亮的**原型水准**，但它管的是"自己的仓"。

易仓 / Flux / 万邑通的本质是**"替别人管仓并收钱"**——
真正缺的核心不是某个页面，而是五根支柱：

> **货主（货权）· 订单（来源）· 计费（收入）· 逆向（利润）· PDA（执行）**

以及支撑它们的**库存台账与单据状态机**。
